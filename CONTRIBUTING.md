# Участие в разработке

Перед изменениями ознакомьтесь с [README](README.md),
[лицензией](LICENSE.md) и [дизайн-системой](docs/design-system.md).
Предлагая код для включения в Walone, предоставляйте его на условиях лицензии
проекта. Не добавляйте чужие материалы без совместимых разрешений и авторства.

## Рабочий процесс

1. Воспроизведите проблему или опишите ожидаемое поведение.
2. Сделайте небольшое изменение по существующим паттернам.
3. Добавьте проверку изменённого поведения, если это новая логика или исправление.
4. Запустите релевантные тесты и анализ. В описании PR укажите результат и
   ограничения проверки, особенно для Windows, реального звука и системных разрешений.

Для сообщений об ошибках указывайте версию приложения, платформу,
архитектуру и шаги воспроизведения. Логи предварительно очищайте от личных
путей, ссылок на приватные записи и данных сессий.

## Проверки

После `fvm install` и получения зависимостей:

```sh
python3 tool/prepare_assets.py
python3 tool/check_migration.py
python3 -m unittest discover -s tool -p '*_test.py'
python3 tool/resource_queue.py .fvm/flutter_sdk/bin/flutter analyze --no-pub
python3 tool/resource_queue.py .fvm/flutter_sdk/bin/flutter test --no-pub --concurrency=1
```

`resource_queue.py` предназначен для macOS/Linux. На Windows запускайте FVM
напрямую. На рабочем Mac используйте очередь и для `pub get`, генераторов,
сборок, нативных интеграционных тестов и временных app-сессий.

Генерируемые ресурсы меняйте через `tool/prepare_assets.py` и аудиоинструменты.
Для Drift используйте `fvm dart run build_runner build`; на рабочем Mac
также через очередь. Не форматируйте несвязанные файлы.

Секреты храните в macOS Keychain или локальных переменных окружения.
Перед публикацией проверяйте файлы Gitleaks; не добавляйте настоящие токены
даже в тесты. Обновление эталона SHA-256 требует проверки причины изменения
каждого ресурса, а не механического принятия новых хешей.
